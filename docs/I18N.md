# Lux: internacionalización (es / en)

> Nota: este documento es una BASE generada con asistencia de IA a partir del código del repositorio. El equipo tiene que revisarlo y reescribirlo con sus palabras antes de usarlo en la entrega. Las traducciones al inglés de los diccionarios también son una base: conviene que las lea alguien del equipo (o un docente de inglés) antes de la defensa.

Requerimiento de Programación: "versión en inglés completa: menús, formularios, mensajes, validaciones y reportes", con un selector de idioma que se recuerde. Este documento describe cómo está resuelto, cómo se agrega una clave o un idioma y qué límites tiene.

## 1. Resumen

- Idiomas: español (`es`, el original) e inglés (`en`).
- Sin dependencias nuevas: un proveedor liviano (`I18nProvider`), el hook `useI18n()` y la función `t(clave, params)`.
- Los textos viven en diccionarios tipados bajo `src/i18n/`. El español es la fuente de las claves: una clave que falta en inglés, o un `{parámetro}` mal escrito, rompe `bun run typecheck`.
- El idioma se guarda en `localStorage` (`lux_lang`) y se aplica a `<html lang>`.
- Fechas, horas y números salen de `Intl` con el locale del idioma activo (`es-UY` / `en-GB`).

## 2. Arquitectura

```
src/i18n/
  index.ts          núcleo: t(), translate(), plain(), formatos, idioma activo
  errors.ts         traducción de los mensajes de error de la API
  types.ts          tipo Translation<T> (mismas claves que el español)
  es/               diccionarios en español (fuente de las claves), uno por dominio
  en/               diccionarios en inglés, mismas claves
  i18n.test.ts      completitud, interpolación, plurales, persistencia, formatos, errores
  literals.test.ts  heurística de literales en español sin traducir
src/hooks/useI18n.ts                        I18nProvider + useI18n()
src/components/accessibility/LanguageSwitcher.tsx   selector ES / EN
src/mocks/spanish.ts                        el mock responde siempre en español
src/test/setup.ts + bunfig.toml             los tests arrancan en español
scripts/i18n-verify.ts                      recorrido real con Chromium (ver sección 7)
```

Claves planas con puntos, por dominio: `tickets.list.empty`, `loans.form.submit`, `validation.user.dni`. Cada archivo de `es/` exporta un objeto `as const` y su par en `en/` se tipa con `Translation<typeof es>`; `es/index.ts` y `en/index.ts` los aplanan en un solo diccionario.

### Cómo se usa

En componentes:

```tsx
const { t, lang, setLang } = useI18n();
<Button>{t("common.save")}</Button>
<p>{t("loans.count", { count: n })}</p>
```

Fuera de componentes (validaciones, constantes, utilidades) se importa `t` de `@/i18n`, que lee el idioma activo en ese momento. Si en el mismo archivo hay un hook `t` y el global, el global se importa como `t as translateNow` para no tapar el nombre (regla `no-shadow` del linter).

### Parámetros y plurales

- Marcadores `{nombre}`; el tipo de `t` exige exactamente los de la clave española.
- Plural: si el texto tiene la forma `"uno | otros"` y se pasa un número en `count`, se elige la forma con `Intl.PluralRules` del idioma. Ejemplo: `"{count} equipo | {count} equipos"`.
- Un marcador sin parámetro queda a la vista tal cual. Se usa a propósito en los avisos (`{o}`, `{by}`), que se resuelven en dos pasos.

### Constantes y etiquetas

`*_LABELS` y `*_STATUS_CONFIG` de `src/lib/constants.ts` siguen exportándose igual, pero sus `label` son getters que resuelven en el idioma activo (`statusConfig(claveEtiqueta, color)` y `labels({...})`). Los consumidores no cambian. Para una clave dinámica fuera de esos mapas se usa `plain(clave, lang?)`.

### Cambio de idioma en caliente

`I18nProvider` suscribe a un almacén de idioma con `useSyncExternalStore` y monta sus hijos con `<Fragment key={lang}>`. Al cambiar el idioma el árbol se vuelve a montar: así se refrescan también los textos que salen de constantes y utilidades, que no son reactivos. El costo es que se pierde el estado local de la pantalla (un formulario a medio llenar, el filtro elegido). La sesión no se pierde porque vive en `localStorage`. Es una decisión de simplicidad; ver "Decisiones" por si el equipo prefiere otra cosa.

### Idioma inicial

1. Lo guardado en `lux_lang`, si es `es` o `en`.
2. Si no hay nada, el idioma del navegador (`navigator.languages`) cuando es `es` o `en`.
3. Si no, español.

El acceso a `localStorage` está envuelto en `try/catch`: sin storage (modo privado, tests) la app funciona y el cambio vale solo para la sesión.

### Selector

`LanguageSwitcher` (dos botones `ES` / `EN` con `aria-pressed`) aparece en el login, en la barra superior de `AppLayout` y `AdminLayout`, y en Perfil junto a las opciones de accesibilidad. También se sincroniza entre pestañas con el evento `storage`.

## 3. Cómo agregar una clave

1. Elegir el archivo del dominio en `src/i18n/es/` y agregar la clave con su texto en español (jerarquía `dominio.sección.texto`).
2. Agregar la misma clave en `src/i18n/en/<mismo archivo>`. Si falta, falla el typecheck.
3. Usarla con `t("dominio.seccion.texto")`.
4. Si el texto en inglés es idéntico al español a propósito (una sigla, "Email"), agregar la clave a `SAME` en `src/i18n/i18n.test.ts`. Ese test existe para detectar traducciones que quedaron copiadas por descuido.
5. Correr `bun test` y `bun run typecheck`.

Convenciones: no concatenar frases con `+` (el orden de las palabras cambia entre idiomas): usar marcadores. No partir una oración en varias claves. Los nombres propios y los datos que carga la gente (nombres, títulos de tickets, ubicaciones) no se traducen.

## 4. Cómo agregar un idioma

1. En `src/i18n/index.ts`: sumar el código a `LANGS` y su locale a `LOCALES` (por ejemplo `pt: "pt-BR"`), y registrarlo en `DICTIONARIES`.
2. Crear `src/i18n/pt/` con un archivo por dominio, copiando `en/` y traduciendo. `pt/index.ts` se tipa como `Record<MessageKey, string>`: el typecheck lista lo que falta.
3. Agregar `language.name.pt` en `es/core.ts` y `en/core.ts` (y en `pt/`) para el botón del selector.
4. Los tests de completitud recorren `LANGS`, no hace falta tocarlos; sí revisar `SAME`.
5. Revisar que `Intl.PluralRules` cubra el idioma (las formas `"uno | otros"` sirven para lenguas con dos formas; con más formas hay que extender `pickPlural`).

## 5. Qué se traduce y cómo

| Área | Cómo |
| --- | --- |
| Menús, barras, login, errores 403/404/500, diálogos, paginación | `useI18n()` |
| Formularios, placeholders, `aria-label`, `title` | `t()` en cada componente |
| Estados, roles, categorías, tipos | getters en `constants.ts` apoyados en `status.*`, `role.*`, etc. |
| Validaciones (`src/lib/validation.ts`) | `t()` global: el mensaje sale en el idioma activo al validar |
| Errores de la API | `ApiError` + `translateError` (ver abajo) |
| Fechas, horas, números, "hace 5 min" | `formatDate`, `formatDateTime`, `formatNumber`, `formatRelativeTime` sobre `Intl` |
| Reportes y CSV | encabezados y nombres de archivo con `t()` (ver abajo) |
| Registro de actividad | las operaciones y entidades (`CREATE_USER`, `Ticket`) se muestran con su nombre en el idioma activo; un código desconocido se muestra tal cual |
| Datos de ejemplo del mock (nombres, tickets, ubicaciones) | no se traducen a propósito: son datos de la gente |

### Errores de la API

La API (y el mock) responden siempre en español. `translateError` (en `src/i18n/errors.ts`) prueba, en orden:

1. `extensions.code` contra `ERROR_CODE_KEYS` (`UNAUTHENTICATED`, `FORBIDDEN`, `INVALID_CREDENTIALS`).
2. Las plantillas de los mensajes conocidos (claves `error.*` y `validation.*` del diccionario español), con sus parámetros. Los parámetros que son etiquetas de dominio ("En progreso", "aprobar") también se traducen por búsqueda inversa.
3. El texto original, sin tocar.

O sea que un mensaje nuevo en la API nunca se rompe: como mucho se ve en español. Si el backend cambia un mensaje, hay que cambiar también la plantilla `error.*` correspondiente (el test de errores cubre las plantillas conocidas). La salida más sólida a futuro es que la API mande siempre un `extensions.code` y que el cliente mapee código a texto.

El mock reproduce esta ruta: `src/mocks/spanish.ts` envuelve las validaciones con `withLang("es")`, así el mock responde en español aunque la interfaz esté en inglés y el cliente traduce, igual que con la API real. La API de `api/` tiene su propia copia de `src/lib` y no se tocó.

### Reportes, CSV, impresión

- Encabezados de columnas y nombres de archivo de los CSV salen del idioma activo (`lux-prestamos-vencidos-...csv` / `lux-overdue-loans-...csv`).
- Números del CSV con `formatNumber` del idioma activo. El separador sigue siendo `;` en ambos idiomas (decisión: Excel en Uruguay lo espera así; con un Excel en inglés puede ser necesario importar el archivo indicando el separador).
- No hay exportación a PDF ni impresión propia en el frontend actual (se buscó `print`/`pdf` en `src/`). El QR (`QrCode`) codifica el ID de máquina, que es un dato, y no lleva texto propio; el lector (`QrScanner`) usa textos de interfaz traducidos.

## 6. Tests

`bun test` incluye (archivos `src/i18n/*.test.ts`):

- Completitud: es y en tienen exactamente las mismas claves, ninguna vacía, mismos marcadores y claves no repetidas entre archivos.
- El inglés no repite el español, salvo la lista `SAME` de términos que se escriben igual.
- Interpolación y plurales (`uno | otros`) en ambos idiomas.
- Persistencia y detección del idioma: guardado, idioma del navegador, español por defecto, storage que lanza excepción.
- Formato de fechas, horas, números y tiempo relativo en ambos locales.
- Traducción de errores de la API (código, plantilla, parámetros, texto desconocido).
- Constantes y validaciones en los dos idiomas.
- Heurística de literales (`literals.test.ts`): recorre `src/` (menos `i18n/`, `mocks/`, `test/` y los tests) y falla si encuentra un literal entre comillas o un texto JSX que parezca español (tildes, `¿ ¡ ñ` o palabras de interfaz como "Guardar"). **Límite**: no entiende código, solo mira texto; una frase en español sin tildes ni palabras de la lista pasa, y un texto armado por partes o que viene de la API tampoco se ve. Es una red de seguridad contra olvidos, no una prueba de que todo esté traducido. Si da un falso positivo, se agrega a `EXCEPCIONES` con el motivo.

## 7. Verificación en navegador

`scripts/i18n-verify.ts` levanta `vite` (con MSW), abre Chromium (`/opt/pw-browsers/chromium`, sin `playwright install`) y recorre con la interfaz en inglés el login, las páginas de error y las pantallas principales de tres roles (solicitante, técnico y root_admin, que también recorre `/admin`). Además envía formularios vacíos para ver las validaciones, prueba credenciales malas y comprueba el selector (persistencia tras recargar, `<html lang>`, detección del navegador). Junta el texto visible y los atributos accesibles, descuenta los datos de ejemplo del mock, y busca palabras en español y claves del diccionario que hayan quedado sueltas. Guarda capturas y un volcado JSON en la carpeta `--out`.

```bash
bun scripts/i18n-verify.ts --out /tmp/lux-i18n-en          # inglés
bun scripts/i18n-verify.ts --lang es --out /tmp/lux-i18n-es # español: busca claves sueltas
```

## 8. Decisiones y su default

Decididas con el criterio recomendado mientras el equipo no podía responder. Todas se pueden revertir.

| Tema | Decisión (default) | Alternativa |
| --- | --- | --- |
| Librería | Sin dependencias: proveedor propio liviano | `react-i18next` o `Lingui` si se necesitan namespaces cargados bajo demanda |
| Claves | Español como fuente, claves planas tipadas | Claves en inglés |
| Idioma inicial | Guardado, si no navegador (es/en), si no español | Siempre español |
| Cambio en caliente | Remontar el árbol (`key={lang}`): simple y completo, pierde el estado local | Hacer reactivas las constantes (más código, sin pérdida de estado) |
| Locale inglés | `en-GB` (día/mes/año, 24 h) | `en-US` invertiría día y mes, confuso para quien comparte datos con Uruguay |
| Locale español | `es-UY` | `es-AR` |
| Errores de la API | Mapa por plantilla del texto en español, con código como prioridad y texto original de respaldo | Que la API devuelva solo códigos |
| CSV | Separador `;`, números con el formato del idioma | Separador por idioma |
| Datos de ejemplo | Quedan en español | Mock bilingüe |
| Nombres de ubicación sugeridos | El nombre sugerido al crear una ubicación ("Laboratorio 3") sale del idioma activo y luego es un dato | Fijarlo en español |
| Descripción del `<head>` (`index.html`) | Queda en español (no es contenido de la app) | Setearla en runtime |

## 9. Límites conocidos

- Cambiar de idioma remonta la pantalla y se pierde lo que estaba escribiendo la persona.
- Los mensajes de error que genere el backend real y no estén en `error.*` se ven en español.
- Los datos que cargan las personas (títulos, comentarios, nombres) no se traducen: un comentario escrito en español se ve en español en la interfaz en inglés.
- El título y la descripción estáticos de `index.html` no cambian con el idioma (`<html lang>` sí).
- `api/` conserva sus mensajes en español; no se tocó.
- La calidad del inglés es una base: no pasó por una revisión humana.
